- **Type:** Product

- **Author(s) / Deciders:** <span class="md-typeset-planned">Project authors and maintainers</span>
- **Question:** What name and identifier will represent the project across repositories, package registries, and documentation?

## Context

<span class="md-typeset-planned">A project name shapes discoverability, CLI/package ergonomics, and brand identity. Choosing a clear, conflict-free name early avoids breaking changes to package identifiers, repository URLs, and namespace imports later.</span>

## Requirements and Restrictions

- <span class="md-typeset-planned">**Pronounceability and Brevity:** Easy to type, pronounce, and remember.</span>
- <span class="md-typeset-planned">**Namespace Availability:** Available on target package registries (such as crates.io, PyPI, npm), GitHub/GitLab, and domain registrars if applicable.</span>
- <span class="md-typeset-planned">**Trademark and Search Collision:** Does not collide with active software projects or registered trademarks in the same domain.</span>

## Alternatives

- <span class="md-typeset-planned">**Candidate A:** Summarize meaning, availability, and why it was or was not selected.</span>
- <span class="md-typeset-planned">**Candidate B:** Summarize meaning, availability, and why it was or was not selected.</span>
- <span class="md-typeset-planned">**Descriptive Functional Name:** Directly states what the tool does, trading uniqueness for immediate clarity.</span>

## Decision

<span class="md-typeset-planned">State the chosen display name, repository slug, and package/CLI binary identifier.</span>

## Consequences

### Positives

- <span class="md-typeset-planned">Consistent naming across the codebase, documentation (`zensical.toml`), and distribution channels.</span>

### Negatives

- <span class="md-typeset-planned">Document any spelling ambiguities or similarity to unrelated terms outside the domain.</span>
